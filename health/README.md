# HealthService

The "HealthService (Python)" of [docs/architecture.md](../docs/architecture.md): it reads the crew's readings, works out
how each measure changed against the person's pre-flight reference, compares it with the NASA bed-rest studies, serves
the 3D page, saves its results and raises alerts. Design and open questions: [docs/health-service.md](../docs/health-service.md).

Until the DataService exists, gravsim (`../sim`) stands in for it in the same process (`GravsimSource`). The simulator's
`truth` and `status` fields are dropped on the way in: the HealthService only sees what instruments would report.

## Run

Python 3.10 or newer.

```bash
cd health
python3 -m venv .venv
.venv/bin/pip install -e ../sim -e ".[dev]"
.venv/bin/python -m pytest -q
.venv/bin/python -m healthservice --day 95 --speed 20 --port 3000
```

Then, in `src/front/sketch` on `main` (a separate checkout; run `npm install` once):

```bash
VITE_DASHBOARD_URL=http://localhost:3000/api/v1/dashboard npm run dev
```

`--speed 20` advances the mission 20 days per real minute, so the page (which polls every 3 seconds) shows it unfolding.

| Endpoint | What it returns |
|---|---|
| `GET /api/v1/dashboard` | Dashboard JSON, contract version 1 (`docs/frontend-backend.md` on `main`). `?crew=CM-2` picks a crew member; `?day=150` looks at that day without saving anything. |
| `GET /api/v1/alerts` | Alerts published so far (`?crew=` to filter), until the notification system defines its queue. |
| `GET /api/v1/health` | Status, crew and current mission day. |
| `GET /docs` | API documentation generated by FastAPI. |

## The pieces

| File | What it does |
|---|---|
| `models.py` | Mission (phases, day labels, days without gravity), crew member and reading, as expected from the DataService. |
| `reference.py` | Curves fitted from the bed-rest data (gravsim's `params.json`; path in `HEALTH_REFERENCE_PATH`). |
| `processing.py` | Reference, change, score and typical change with and without exercise, per measure. Ported from gravsim's `dashboard.py`. |
| `dashboard.py` | Builds the JSON for the 3D page from those results. |
| `alerts.py` | Alert rule (below) and an in-memory queue. |
| `sources.py` | What the HealthService needs from the DataService, and `GravsimSource`, which stands in for it. |
| `service.py` | Ties it together. Results are saved and alerts raised only when new readings arrive, not on every poll. |
| `api.py`, `__main__.py` | HTTP API (FastAPI) and command line. |
| `evaluation/alert_rule.py` | Scores alert rules against gravsim's `truth` (below). |

## Alert rule

A measure raises an alert when its last two tests since launch, on average, have gone beyond the typical change
bed-rest subjects had without exercise after the same days without gravity, by more than 1.645 times the
measurement noise of that average (noise alone gets that far once in 20 times). The noise comes from the test-retest
variability fitted from the bed-rest data and the number of pre-flight tests in the reference. Only measures whose
typical loss without exercise over the mission is bigger than the noise of one test can alert. On the ISS schedule
that leaves out two measures, which are still shown on the page:

- ankle dorsiflexion: about -7% against 12% noise;
- arm lean mass: it does not change in bed rest.

`.venv/bin/python evaluation/alert_rule.py` (about 20 s) compares rules on gravsim crews and scores each alert with
`truth`. An alert counts as false when the person's true change has not gone beyond the typical change without
exercise. It counts readings from launch to 30 days after landing.

| Crew | Old rule (one test beyond typical): alerts, false | This rule: alerts, false |
|---|---|---|
| Demo crew (seed 7, 4 people) | 28, 28 | 0, 0 |
| 50 random missions (200 people) | 1421, 1214 | 16, 11 |
| Same, with 1 in 10 dynamometer tests off by 20% | 1548, 1348 | 29, 20 |
| 7 designed cases x 25 people | 1459, 907 | 117, 15 |

Results per person during flight, in the designed cases:

- All 25 people who skip exercise and lose fast are alerted (median first alert on day 74).
- Of the 25 typical people who skip exercise, 17 reach a clear loss (5 or more points beyond typical), and 14 of
  those are alerted.
- None of the 25 who follow the routine is alerted.
- Of the false alerts, 14 of 15 are within 3 points of the line; most are hip bone density after landing, in people
  who did not exercise.

## Checks

`tests/test_healthservice.py` (28 checks):

- The dashboard is identical to gravsim's own builder for 4 crew members on 9 mission days, before, during and after flight (only the notice text differs).
- Every dashboard passes the contract checks (gravsim's Python copy of `contract.js`).
- Days without gravity match gravsim's calculation.
- Results are saved only when new readings arrive; looking at a past day saves nothing.
- Over a whole flight, the demo crew raises no alert.
- A crew member who skips exercise and loses fast is alerted, and one who follows the routine is not.
- Each alert is published once while it lasts.
- Ankle dorsiflexion and arm lean mass cannot alert.
- The evaluation scores exactly what `alerts.check` does.

## Known limits

- **The alert rule is cautious.** Each dynamometer test carries 8-12% noise, about as much as the difference between
  people. That has three effects:
  - Most readings that are only a few points beyond the line go unflagged.
  - An alert needs two tests, and the dynamometer is monthly, so the first one comes on day 44 at the earliest.
    Publishing a finding after one test, so the analysis scheduler can order an earlier retest, would shorten that
    (docs/health-service.md, question 9).
  - An injury in someone who exercises rarely goes beyond the no-exercise line, and it heals between monthly tests:
    1 of 16 was alerted. Catching that needs comparing with the person's own trend, not with the bed-rest groups.
- Results are kept in memory (`GravsimSource.saved_results`) until the DataService can store them.
- Bed rest is NASA's ground analog for weightlessness, not spaceflight, and every number here is synthetic.
