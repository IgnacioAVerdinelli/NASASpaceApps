# HealthService

**Local demo update:** `python -m healthservice.demo --queue PATH` consumes DataService events, processes all crew members, publishes findings for the Planner (`health.finding`) and health notices (`health.notice`, [contract v1](../docs/health-notices.md)), and records simulated deliveries. Studies are booked by the Planner (`planner/`). The queue can also come from `NASA_QUEUE`; `python -m healthservice.notices` publishes synthetic fixtures and consumes the queue from another process. Start all components as described in the [root README](../README.md). `python -m healthservice --queue PATH` exposes the delivery log at `/api/v1/deliveries`. In this mode processing is not limited to dashboard requests; the known limitation below applies to running the HealthService without the demo worker.

The "HealthService (Python)" of [docs/architecture.md](../docs/architecture.md): it reads the crew's readings from the
DataService, works out how each measure changed against the person's pre-flight reference, compares it with the NASA
bed-rest studies, serves the 3D page, saves its results through the DataService and raises alerts. Design and open
questions: [docs/health-service.md](../docs/health-service.md).

It reads the DataService's HTTP API (`python -m gravsim.serve`, port 8000): the mission and crew from
`GET /api/v1/mission`, readings from `GET /api/v1/readings`, and it saves with `POST /api/v1/results`. Only readings
with quality `ok` count. The DataService does not send the simulator's `truth` and `status` fields by default, and the
HealthService would drop them anyway: it only sees what instruments would report.

## Run

Python 3.10 or newer.

```bash
cd health
python3 -m venv .venv
.venv/bin/pip install -e ../sim -e ".[dev]"
.venv/bin/python -m pytest -q
```

Then three terminals, from the root of the repository:

```bash
health/.venv/bin/python -m gravsim.serve --day 95 --speed 20      # DataService, port 8000
```

```bash
health/.venv/bin/python -m healthservice                          # HealthService, port 3000
```

```bash
cd src/front/sketch && npm install && npm run dev
```

`--speed 20` advances the mission 20 days per real minute, so the page (which polls every 3 seconds) shows it
unfolding. The HealthService follows the DataService's clock. `python -m healthservice --gravsim --day 95 --speed 20`
runs gravsim's DataService inside the HealthService instead, with no other server.

| Endpoint | What it returns |
|---|---|
| `GET /api/v1/dashboard` | Dashboard JSON, contract version 1 ([docs/frontend-backend.md](../docs/frontend-backend.md)). `?crew=CM-2` picks a crew member; `?day=150` looks at that day without saving anything. |
| `GET /api/v1/analyses` | Flight-measurement JSON for `vuelo.html` (strength and aerobic capacity tabs): each test with its level, whether it is within test noise, the measure's alert and the upcoming tests ([docs/frontend-backend.md](../docs/frontend-backend.md#mediciones-en-vuelo-get-apiv1analyses)). Same `?crew=` and `?day=` as the dashboard; 404 for an unknown crew member. |
| `GET /api/v1/vitals` | The watch (layer 1, [docs/wearable.md](../docs/wearable.md)): each daily vital (resting heart rate, pressure, SpO2, HRV, sleep) against the person's own last two weeks, its status and 30 days of values; the fatigue pattern; the watch's heart rate today, yesterday, a week ago and on an average pre-flight day, with today's sleep, exercise and spacewalks. Same `?crew=` and `?day=`. |
| `GET /api/v1/alerts` | Alerts published so far (`?crew=` to filter), until the notification system defines its queue. |
| `GET /api/v1/health` | Status, crew and current mission day. |
| `GET /docs` | API documentation generated by FastAPI. |

If the DataService does not answer, `/dashboard` and `/health` answer 503 with the reason, and the page shows
"Unable to load data" and keeps retrying.

## What it saves

On each update with new readings, one result per crew member, through `POST /api/v1/results`:

```json
{
  "crew_id": "CM-1", "kind": "measure_results", "timestamp": "2027-04-06T12:00:00Z", "model_version": "0.2.0",
  "payload": {
    "mission_day": 95.0,
    "measures": {
      "knee_extension_60": {
        "unloaded_days": 95.0, "reference_value": 124.5, "reference_n": 2,
        "last_value": 121.3, "last_reading_at": "2027-03-16T12:00:00Z", "last_mission_day": 74.0, "change_pct": -2.6,
        "previous_change_pct": 3.5, "previous_mission_day": 44.0, "score": 11.1,
        "typical_no_exercise_pct": -22.68, "typical_exercise_pct": -8.23, "extrapolated": false, "synthetic": true
      },
      "knee_flexion_60": {"...": "the other 7 measures, the same fields"}
    }
  }
}
```

(CM-1 of the demo crew on day 95; the typical changes are not rounded in the real record.)

All the measures go in one record because the DataService keeps one result per crew member, kind, time and model
version: one record per measure at the same time would overwrite each other. The fields of each measure are those of
`MeasureResult` in `processing.py`.

## The watch (vitals.py)

Layer 1 of [docs/wearable.md](../docs/wearable.md). For each daily vital, a personal band from the 14 days before the last 3 (mean ± 2 SD, with an SD floor). A **deviation** is the mean of the last 3 days beyond 2.5 SD of a 3-day mean, the bad way, with each of those days on the worse side of the usual mean; SpO2 under 92 % counts at once. The demo worker checks it whenever the wearable's or the watch's daily values arrive and publishes a `health.finding` with `"source": "watch"` (`suspected`, then `cleared`), which the Planner turns into a review. The watch's 15-minute heart rate alone triggers nothing, and no longer runs the strength and VO2peak processing. Every number is ours, not NASA's.

The default DataService URL is now `http://127.0.0.1:8000`: on Windows `localhost` tries IPv6 first and costs about 2 s per request.

## The pieces

| File | What it does |
|---|---|
| `models.py` | Mission (phases, day labels, days without gravity), crew member and reading, as the DataService sends them. A reading with no mission day is placed by its timestamp. |
| `reference.py` | Curves fitted from the bed-rest data (gravsim's `params.json`; path in `HEALTH_REFERENCE_PATH`). |
| `processing.py` | Reference, change, score and typical change with and without exercise, per measure. Ported from the dashboard builder of gravsim 0.1.0. |
| `dashboard.py` | Builds the JSON for the 3D page from those results. |
| `contract.py` | Python copy of the page's checks (`src/front/sketch/data/contract.js`), for the tests. |
| `alerts.py` | Alert rule (below) and an in-memory queue. |
| `findings.py` | Findings for the Planner, with their state: `suspected` after one test past the noise, `confirmed` with the alert, `cleared` when neither holds. The last one per measure is kept in the DataService (kind `finding`). See [docs/health-service.md](../docs/health-service.md#hallazgo-y-aviso). |
| `notices.py` | Health notices for the Notification Center (contract v1, issue #11): routing by priority and context, revisions, mission location, and a command line to publish fixtures and consume the queue. See [docs/health-notices.md](../docs/health-notices.md). |
| `demo.py` | Queue worker: processes `data.readings_stored`, publishes findings and notices, and stands in for the Notification Center's deliveries. |
| `sources.py` | What the HealthService needs from the DataService: `DataServiceSource` (HTTP) and `GravsimSource` (gravsim's DataService in the same process, for tests and the evaluation). |
| `levels.py` | Levels 1 to 4 of a test (below) and the noise band of one test. |
| `analyses.py` | Builds the JSON for the flight-measurement page (`vuelo.html`) from the same results, alerts and the tests the Planner booked. |
| `service.py` | Ties it together. Results are saved and alerts raised only when new readings arrive, not on every poll. |
| `api.py`, `__main__.py` | HTTP API (FastAPI) and command line. |
| `evaluation/alert_rule.py` | Scores alert rules against gravsim's `truth` (below). |

## Alert rules

There are two. Each alert carries its `rule` and a `severity`:

| Rule | Severity | Measures | Means |
|---|---|---|---|
| `nasa_standard` | `critical` | VO2peak | NASA's in-mission standard for aerobic capacity was crossed. |
| `beyond_typical` | `warning` | all with enough signal (below) | The loss is faster than bed-rest subjects had without exercise. |

When both apply to a measure, the critical one is published. An alert is published again when its severity changes.

### NASA standard (VO2peak)

VO2peak raises a critical alert when its last two tests since launch, on average, are 20% or more below pre-flight
(a loss of performance, OCHMO-TB-031) or below 32.9 ml/kg/min (the in-mission minimum, NASA-STD-3001 Vol 1
[V1 4001]). It does not depend on bed rest: the standard is about what the crew member can still do. It uses the mean
of two tests, like the other rule, because one cycle test carries enough noise to cross the line by itself.

Scored the same way as the other rule (an alert is false when the person's true VO2peak, in gravsim's `truth`, is not
past the standard):

| Crew | Alerts | False | Tests past the standard caught |
|---|---|---|---|
| Demo crew (seed 7, 4 people) | 3 | 2 | 4/5 |
| 50 random missions (200 people) | 65 | 22 | 132/177 |
| 7 designed cases x 25 people | 81 | 12 | 233/278 |

In the demo crew, CM-1 is alerted on FD165, and it is real: its true VO2peak is 32.0, below the minimum. Both false
alerts are CM-2's, whose true VO2peak stays just above the minimum (33.8 on FD75, 34.5 on R+30): on FD75 two low
tests (31.5 and 32.2) pull the mean under 32.9, and on R+30 one very low test (30.1) does. The rule also runs after
landing, although the 32.9 minimum is NASA's in-mission standard; whether it should stop at landing is open.

Strength has no such rule. With 8 to 12% noise per dynamometer test, "20% below pre-flight" on the mean of two
tests was false for 53 of 57 quadriceps alerts in the 200 random crew members.

### Faster loss than expected (all measures)

A measure raises an alert when its last two tests since launch, on average, have gone beyond the typical change
bed-rest subjects had without exercise after the same days without gravity, by more than 1.645 times the
measurement noise of that average (noise alone gets that far once in 20 times). The noise comes from the test-retest
variability fitted from the bed-rest data and the number of pre-flight tests in the reference. Only measures whose
typical loss without exercise over the mission is bigger than the noise of one test can alert. On the ISS schedule
that leaves out two measures, which are still shown on the page:

- ankle dorsiflexion: about -7% against 12% noise;
- arm lean mass: it does not change in bed rest.

`.venv/bin/python evaluation/alert_rule.py` (about 5 s) compares rules on gravsim crews and scores each alert with
`truth`. An alert counts as false when the person's true change has not gone beyond the typical change without
exercise. It counts readings from launch to 30 days after landing. Numbers with gravsim 0.2.0:

| Crew | Old rule (one test beyond typical): alerts, false | This rule: alerts, false |
|---|---|---|
| Demo crew (seed 7, 4 people) | 28, 26 | 0, 0 |
| 50 random missions (200 people) | 1489, 1340 | 11, 6 |
| Same, with 1 in 10 dynamometer tests off by 20% | 1555, 1419 | 27, 19 |
| 7 designed cases x 25 people | 1494, 1023 | 87, 11 |

Results per person during flight, in the designed cases:

- Of the 25 people who skip exercise and lose fast, 23 are alerted (median first alert on day 74).
- Of the 25 typical people who skip exercise, 9 reach a clear loss (5 or more points beyond typical), and 6 of those
  are alerted.
- None of the 25 who follow the routine is alerted.
- Of the 11 false alerts, 9 are within 3 points of the line, and 8 are hip bone density after landing, in people who
  did not exercise.

## Checks

`tests/test_healthservice.py` (27 checks):

- Every dashboard passes the page's contract checks, for 4 crew members on 9 mission days, before, during and after
  flight.
- Reference, change, previous change, score, typical changes, labels and chart points match a case worked out by
  hand; readings flagged by the DataService are left out.
- Days without gravity match gravsim's calculation; a reading with no mission day is placed by its timestamp.
- Results are saved, one record per crew member and moment, only when new readings arrive; looking at a past day
  saves nothing.
- Over a whole flight, the demo crew raises no "faster loss than expected" alert, and the NASA-standard alert only
  for CM-1 and CM-2's VO2peak; a crew member who skips exercise and loses fast is alerted, and one who follows the
  routine is not; each alert is published once while it lasts.
- Ankle dorsiflexion and arm lean mass cannot alert.
- The evaluation scores exactly what `alerts.check` does.
- Against gravsim's DataService API on a free port: the HTTP source reads the same mission, crew, readings and
  dashboards as the in-process one, and saves its results there. If the DataService is down, the API answers 503.

`tests/test_analyses.py` (18 checks), for `GET /api/v1/analyses`:

- Every response passes the page's contract checks, for 4 crew members on 11 days from pre-flight to R+365.
- Level boundaries (5, 10 and 20% worse) and the NASA minimum; the noise band of one test (16.8 points for knee
  extension against a 2-test reference); a case worked out by hand.
- One VO2peak test past the standard is shown as level 4 but not alerted.
- The page shows the same numbers as the dashboard and the same alerts the queue gets.
- Upcoming tests come from the Planner's plan (kind `plan`), read over HTTP; a retest goes to the tab of its
  measure.

`tests/test_demo.py` (4 checks) covers the demo worker.

`tests/test_findings.py` (6 checks), for the findings the Planner reads:

- One strength test far past the no-exercise curve is `suspected` (level, `beyond_noise` above 1), not an alert. A
  test inside the noise gives no finding.
- The same measure goes `suspected` → `confirmed` → `cleared` as tests come in, and `cleared` is published once.
- One VO2peak test below NASA's minimum is `suspected` by `nasa_standard` and raises no alert.
- Over a whole flight, a crew member who skips exercise gets a `suspected` finding before the first `confirmed` one.
  The one who follows the routine gets no `confirmed` strength finding.
- The worker publishes each finding once, however many times it processes the same readings, and keeps the last one
  per measure in the DataService.

## Known limits

- **Results and alerts are only worked out when someone asks for a dashboard**, and only for that crew member. The
  DataService's events do not cross processes yet (its publisher is a mock), so nothing tells the HealthService that
  new readings arrived. A loop that updates every crew member every few seconds would fix it until the events exist.
- **The alert rule is cautious.** Each dynamometer test carries 8-12% noise, about as much as the difference between
  people. That has three effects:
  - Most readings that are only a few points beyond the line go unflagged.
  - An alert needs two tests, and the dynamometer is monthly, so the first one comes on day 44 at the earliest.
    A `suspected` finding after one test lets the Planner book an earlier retest (`findings.py`).
  - An injury in someone who exercises rarely goes beyond the no-exercise line, and it heals between monthly tests:
    of the 19 with a clear loss, 1 was alerted. Catching that needs comparing with the person's own trend, not with
    the bed-rest groups.
- The DataService keeps the saved results in memory (its SQLite store is not wired yet).
- Bed rest is NASA's ground analog for weightlessness, not spaceflight, and every number here is synthetic.
